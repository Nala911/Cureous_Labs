# CUREOUS ZOHO CREATOR IMPLEMENTATION & ARCHITECTURAL PROTOCOL

This document defines the permanent collaboration protocol, design standards, Deluge scripting rules, and file management principles for building the Cureous Patient Repositioning System (PRS) application in Zoho Creator.

---

## 1. Module-by-Module Iterative Process

1. **Module Alignment & Brainstorming**:
   - Before starting any module, the user explains the operational purpose, day-to-day user journey, and required workflows.
   - The assistant evaluates the requirements and recommends the most user-friendly, clean, and robust architecture leveraging Zoho Creator native features:
     - **Form Workflows** (On Load, On User Input, On Validate, On Success)
     - **Blueprints** (for stage transitions, step gates, and checklist enforcement)
     - **Approvals** (for managerial overrides, commercial waivers, write-offs)
     - **Schedules & Batch Workflows** (for daily billing, automated ledger rollups)
     - **Functions / Standalone Deluge** (for reusable business logic)
   - Every workflow is designed to prevent hitting Deluge execution statement limits (5,000 statements/run) and optimize Zoho One subscription quotas.

2. **Schema & Field Finalization**:
   - Agree on exact field types, display labels, mandatory/unique rules, and **Field Link Names** (API names).
   - The user provides or validates actual Field Link Names generated by Zoho Creator to ensure zero syntax errors in Deluge scripts.

3. **Master Documentation & Modular Architecture**:
   - The project documentation is maintained in modular Markdown files under `docs/`:
     - `docs/ARCHITECTURE.md`: System overview, product lifecycles, Books integration, and roles.
     - `docs/DATA_DICTIONARY.md`: **The Master Dependency Matrix**. Maps every field, link name, type, and cross-module reference. Checked and updated on every schema or workflow change.
     - `docs/modules/<xx_module>.md`: Dedicated specification file for each individual module.
   - **NO inline Deluge script blocks in module plan files.** All business logic must be stated in **plain English** and reference the exact file path of the corresponding script in `scripts/`.
   - **NO premature Reports, Views, or UI designs in plan files.** Deferred until forms, relationships, and workflows are completely built and tested.
   - When schemas or workflows change during iterative discussion, the module file and `DATA_DICTIONARY.md` are immediately refactored to remain 100% accurate.
   - **NO trailing historical/changelog bloat.** When fields, schemas, or logics are removed or modified, remove or refactor them cleanly in-place.

4. **Script Generation & Organization**:
   - All Deluge code is saved in standalone, modular files under `scripts/<module_or_area>/`.
   - Clean, descriptive file names indicating the exact workflow hook (e.g. `2_1_Devices_onuserinput_serialnumber.deluge`).

## 2. Directory & Script Architecture

All scripts are categorized into dedicated module folders:
```
scripts/
├── 02_customers/
├── 03_offices/
├── 05_devices/
│   ├── form_devices/
│   ├── stateless_update_stage/
│   ├── stateless_update_custody/
│   └── report_all_devices/
├── 07_deployments/
└── functions/
```

### Form-Based Subfolder Standard for Multi-Form Modules
- **Single-Form Modules**: If a module contains only one primary form (e.g. `02_customers/`, `03_offices/`), scripts remain flat directly inside `scripts/<module>/`.
- **Multi-Form Modules**: Whenever a module contains more than one form (e.g. primary database form + stateless action forms or wizards), the module directory must be subdivided into form-specific subfolders:
  - `form_<form_link_name_lowercase>/` for the primary database form (e.g. `form_devices/`).
  - `stateless_<action_name_lowercase>/` for stateless utility forms or wizards (e.g. `stateless_update_stage/`, `stateless_update_custody/`).
  - `report_<report_link_name_lowercase>/` for report custom actions, bulk launcher functions, and record action items (e.g. `report_all_devices/`).
- **Sequential Integrity**: Inside each subfolder, scripts strictly follow the chronological trigger sequence (`1_`, `2_`, `3_`, `4_`, `5_`) without file collision across forms.

### Zoho Creator Naming, Navigation & Action Button Standard
- **Consistent Form Naming**:
  - **Primary Database Forms**: Plural noun (e.g., `Devices`, `Deployments`, `Customers`, `Offices`).
  - **Stateless Wizard Forms**: `<Verb>_<Noun>` (e.g., `Update_Device_Stage`, `Update_Device_Custody`, `Bulk_Deploy_Devices`, `Swap_Deployment_Device`, `Close_Deployment`).
- **Sidebar Navigation**: Keep only primary database modules at the root of the sidebar. Hide stateless wizard forms from the main menu or group them under a collapsed `Wizards & Utilities` section, launching them via Report Action Buttons.
- **Function Namespaces**: Group report custom action launcher functions into module-specific namespaces (e.g., `devices_actions`, `deployments_actions`) instead of leaving them in `Default`.
- **3-Tier Action Button Placement**:
  1. **Report Header / Top Bar** *(No record selection)*: Bulk creation wizards (e.g., `Bulk Deploy`).
  2. **Single Record / Detail View** *(1 row)*: Record-specific actions with condition guards (e.g., `Swap Device`, `Close Deployment` when `State != "Returned"`).
  3. **Multiple Records** *(Checkbox selection)*: Batch updates across selected rows (e.g., `Update Stage`, `Update Custody`).

### Standardized Documentation Tracking for Stateless Forms
- **Module Doc Action Map (`docs/modules/<xx_module>.md`)**: Every multi-form module doc must maintain a **Stateless Wizards & Action Buttons Table** at the top of its Stateless Utilities / Action Buttons section using these exact columns:
  `| Action Button Label | Report & Placement | Condition | Launcher Function & Namespace | Target Stateless Form | Script Folder |`
- **Master Data Dictionary (`docs/DATA_DICTIONARY.md`)**: Every stateless form must have its own subsection under its parent module documenting its UI fields, **Pre-fill URL Parameters** (e.g., `?Select_Devices=...`, `?Deployment_ID=...`), and cross-form updates.

### Script File Naming Standard
Every `.deluge` file must strictly follow this standardized naming pattern:
`<trigger_number>[_<user_step>]_<FormName>_<trigger_type>[_<detail>].deluge`

Trigger Numbering Sequence:
- `1` = On Load (`1_<FormName>_onload.deluge`)
- `2_1`, `2_2`, `2_3`... = On User Input in chronological user-entry order (`2_<step>_<FormName>_onuserinput_<fieldname>.deluge`)
- `3` = On Validate (`3_<FormName>_onvalidate.deluge`)
- `4` = On Success (`4_<FormName>_onsuccess.deluge`)
- `5+` = Custom Actions / Functions / Schedules (`5_1_<FormName>_onclick_<action>.deluge`)

### Script File Header Standard
Every `.deluge` file must begin with this standardized single-line comment header:
```deluge
// ==============================================================================
// Module Name  : <Module Name> (Form Link Name: <Form_Link_Name>)
// Script Type  : Form Workflow / Function / Schedule / Blueprint Action
// Trigger Hook : <e.g. On User Input of Field_X | On Validate | On Success>
// File Path    : scripts/<folder>[/<subfolder>]/<filename>.deluge
// Fields Used  : [<Field_1>, <Field_2>, ...]
// Cross-Forms  : [<Related_Form_1>, ...]
// Purpose      : <Plain English summary of what this code executes>
// Optimization : <Notes on statement efficiency, batching, or query guards>
// ==============================================================================
```

## 3. Deluge Compiler Laws & Zero-Failure Coding Rules

These rules are permanent and mandatory across all scripts in this project to prevent Deluge compiler crashes and `Improper Statement` errors:

### Law 1: Criteria Brackets `[ ... ]` Integrity
1. **NO Method Calls or Function Calls Inside `[ ... ]`**:
   - Deluge translates `[...]` directly into database queries. Expressions like `.toLong()`, `.toString()`, `.trim()`, or custom functions inside criteria brackets crash the Deluge parser.
   - **Violation**: `dev = Devices[ID == cu_id.toLong()];` (Triggers `Improper Statement` on enclosing block header).
   - **Correct**: Always evaluate and assign variables *before* the criteria:
     ```deluge
     target_id = cu_id.toLong();
     dev = Devices[ID == target_id];
     ```
2. **Strict Data-Type Parity in Criteria**:
   - `NUMBER` fields (`ID`, Number, Currency) can ONLY be compared against `NUMBER` variables (`[ID == number_var]`).
   - `TEXT` fields (`Serial_Number`, Single Line, Dropdown) can ONLY be compared against `TEXT` variables (`[Serial_Number == text_var]`).
   - Comparing mismatched types triggers: `In Criteria left expression is of type NUMBER and right expression is of type TEXT and the operator == is not valid`.
3. **Clean Variable Matching**:
   - Never use dot-navigation inside criteria (e.g. `[Device_Ref == dev.ID]`). Extract to a local variable first:
     ```deluge
     d_id = dev.ID;
     rec = Form[Device_Ref == d_id];
     ```

### Law 2: `insert into` Task Syntax
1. **NO Semicolons and NO Commas Inside `[ ... ]`**:
   - Field assignments inside `insert into Form [ ... ]` are structural assignments separated ONLY by newlines.
   - Putting semicolons (`;`) or commas (`,`) after field lines inside the brackets crashes the Deluge parser with a misleading `Improper Statement` on the outer enclosing block.
   - **Correct Syntax**:
     ```deluge
     insert into Target_Form
     [
         Field_1 = val1
         Field_2 = val2
         Field_3 = val3
     ]
     ```
   - When capturing the generated record ID:
     ```deluge
     new_id = insert into Target_Form
     [
         Field_1 = val1
         Field_2 = val2
     ];
     ```
2. **NO Inline Comments Inside `insert into [ ... ]`**:
   - Never place `//` or `/* */` comments inside square brackets of an `insert into` block.

### Law 3: Record Updates (DML)
- To update an existing record, fetch it first into a variable and assign fields directly:
  ```deluge
  dev = Devices[Serial_Number == serial];
  if(dev != null)
  {
      dev.Rental_State = "Active";
      dev.Current_Customer = cust_id;
  }
  ```
- **NEVER use SQL-style `update Form [Criteria] [...]`**: Deluge does not support SQL syntax.

### Law 4: Collection & Multi-Select Iteration
1. **Iterate Native Fields Directly**:
   - Multi-Select lookups and choice fields already evaluate to collections. Iterate them directly:
     ```deluge
     if(input.Select_Devices != null)
     {
         for each dev_serial in input.Select_Devices
         {
             dev = Devices[Serial_Number == dev_serial];
         }
     }
     ```
   - **Avoid unneeded intermediate list boxing**: Creating in-memory lists (`all_items = list()`) and populating them via `.add()` strips compile-time schema type information, causing the compiler to fail type checks inside the loop.
2. **List Constructor Casing**:
   - If declaring an empty list, always use lowercase `list()` (e.g. `items = list();`), never capitalized `List()`.

### Law 5: Form Workflow Safety & Boundaries
1. **NO `try-catch` in Form Workflows**:
   - Form Workflows (On Load, On User Input, On Validate, On Success) do NOT support `try { ... } catch (e) { ... }`.
   - `try-catch` is strictly reserved for **Standalone Deluge Functions** under `scripts/functions/`.
2. **NO `return` in Form Workflows**:
   - `return;` is an invalid keyword in event workflows (On Load, On User Input, On Validate, On Success). Using `return` crashes the Deluge compiler with `Improper Statement` on the enclosing block header. Use structured `if-else` branching to control execution flow.
3. **NO System Timestamps on `input`**:
   - `input.Added_Time` and `input.Modified_Time` are not accessible on `input` in form workflows. Use `zoho.currentdate` / `zoho.currenttime`.
4. **Single-Line Comments Only**:
   - Always use `//` for comments in form workflows. Never use multi-line `/* ... */` blocks in workflow scripts to prevent line offset misreporting in the Creator compiler.
5. **NO UI Commands (`show`, `hide`, `disable`, `enable`) on Auto-Number or Formula Fields**:
   - Auto-Number and Formula fields are system-managed fields. Calling `show`, `hide`, `disable`, or `enable` crashes the Deluge compiler with: `'<action>' function cannot be applied for '<Field_Name>'`. Auto-number fields are managed purely by Creator layout properties and cannot be targeted by script UI tasks.

## 4. Deluge & Zoho One Optimization Guidelines

To guarantee high performance and avoid quota/statement bottlenecks:
1. **Never query inside loops**:
   - *Bad*: Querying related records for every row of a subform inside a `for each` loop.
   - *Good*: Collect IDs into a `List`, execute a single batch query `[ID in list_of_ids]`, store results in a `Map`, and retrieve in $O(1)$.
2. **Lean Field Footprint**:
   - Use Zoho Creator's native field formulas, default values, and lookup conditional filters where possible before falling back to Deluge script.
3. **Use Blueprints for Life Cycles**:
   - For multi-stage assets, orders, or transfers, use Zoho Creator Blueprints to define states, transitions, required transition fields, and validation rather than writing complex custom stage validation scripts.

## 5. Schema Alignment & Verification Protocol

Before writing or modifying any workflow code:
1. **Mandatory Schema Verification**:
   - Confirm exact internal **Form Link Name** (e.g., `Product_Models` vs `Product_Model`).
   - Confirm exact internal **Field Link Names** for all referenced fields.
   - Confirm exact **Field Data Types** (e.g., is the field storing a `TEXT` Serial Number or a `NUMBER` Record ID?).
2. **Data Dictionary Synchronization**:
   - Update `docs/DATA_DICTIONARY.md` before generating code.
   - Verify all cross-form lookups and dependencies against the matrix.
