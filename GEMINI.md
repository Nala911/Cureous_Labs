# CUREOUS ZOHO CREATOR IMPLEMENTATION & ARCHITECTURAL PROTOCOL

This document defines the permanent collaboration protocol, design standards, Deluge scripting rules, and file management principles for building the Cureous Patient Repositioning System (PRS) application in Zoho Creator.

---

## 1. Module-by-Module Iterative Process

1. **Module Alignment & Brainstorming**:
   - Before starting any module, the user explains the operational purpose, day-to-day user journey, and required workflows.
   - The assistant evaluates the requirements and recommends the most user-friendly, clean, and robust architecture leveraging Zoho Creator native features:
     - **Form Workflows** (On Load, On User Input, On Validate, On Success)
     - **Blueprints** (for stage transitions, step gates, and checklist enforcement)
     - **Approvals** (for managerial overrides, commercial waivers, write-offs)
     - **Schedules & Batch Workflows** (for daily billing, automated ledger rollups)
     - **Functions / Standalone Deluge** (for reusable business logic)
     - **Stateless Wizards** (for guided bedside actions, swaps, multi-bed handovers)
   - Every workflow is designed to prevent hitting Deluge execution statement limits (5,000 statements/run) and optimize Zoho One subscription quotas.

2. **Schema & Field Finalization**:
   - Agree on exact field types, display labels, mandatory/unique rules, and **Field Link Names** (API names).
   - The user provides or validates actual Field Link Names generated by Zoho Creator to ensure zero syntax errors in Deluge scripts.

3. **Master Documentation & Modular Architecture**:
   - The project documentation is maintained in modular Markdown files under `docs/`:
     - `docs/ARCHITECTURE.md`: System overview, product lifecycles, Books integration, and roles.
     - `docs/DATA_DICTIONARY.md`: **The Master Dependency Matrix**. Maps every field, link name, type, and cross-module reference. Checked and updated on every schema or workflow change.
     - `docs/modules/<xx_module>.md`: Dedicated specification file for each individual module.
     - `docs/wizards/<wizard_name>.md`: Detailed specs for stateless popup modals.
   - **NO inline Deluge script blocks in module plan files.** All business logic must be stated in **plain English** and reference the exact file path of the corresponding script in `scripts/`.
   - **NO premature Reports, Views, or UI designs in plan files.** Deferred until forms, relationships, and workflows are completely built and tested.
   - When schemas or workflows change during iterative discussion, the module file and `DATA_DICTIONARY.md` are immediately refactored to remain 100% accurate.
   - **NO trailing historical/changelog bloat.** When fields, schemas, or logics are removed or modified, remove or refactor them cleanly in-place.

4. **Script Generation & Organization**:
   - All Deluge code is saved in standalone, modular files under `scripts/<module_or_area>/`.
   - Clean, descriptive file names indicating the exact workflow hook (e.g. `on_user_input_lot_id.deluge`, `on_validate_dispatch_guard.deluge`).

### Script File Naming Standard
Every `.deluge` file must strictly follow this standardized naming pattern:
`<trigger_number>[_<user_step>]_<FormName>_<trigger_type>[_<detail>].deluge`

Trigger Numbering Sequence:
- `1` = On Load (`1_<FormName>_onload.deluge`)
- `2_1`, `2_2`, `2_3`... = On User Input in chronological user-entry order (`2_<step>_<FormName>_onuserinput_<fieldname>.deluge`)
- `3` = On Validate (`3_<FormName>_onvalidate.deluge`)
- `4` = On Success (`4_<FormName>_onsuccess.deluge`)
- `5+` = Custom Actions / Functions / Schedules

Examples:
- `1_Lots_onload.deluge`
- `3_Lots_onvalidate.deluge`
- `4_Lots_onsuccess.deluge`
- `1_Customers_onload.deluge`
- `2_1_Customers_onuserinput_customername.deluge`
- `3_Customers_onvalidate.deluge`
- `4_Customers_onsuccess.deluge`
- `1_Stock_Transfers_onload.deluge`
- `2_1_Stock_Transfers_onuserinput_transfertype.deluge`
- `2_2_Stock_Transfers_onuserinput_sourceoffice.deluge`
- `2_3_Stock_Transfers_onuserinput_sourcecustomer.deluge`
- `2_4_Stock_Transfers_onuserinput_selectcontrolunit.deluge`
- `2_5_Stock_Transfers_onuserinput_selectoverlay.deluge`
- `3_Stock_Transfers_onvalidate.deluge`
- `4_Stock_Transfers_onsuccess.deluge`

### Script File Header Standard
Every `.deluge` file must begin with this standardized header:
```deluge
/* ==============================================================================
   Module Name  : <Module Name> (Form Link Name: <Form_Link_Name>)
   Script Type  : Form Workflow / Function / Schedule / Blueprint Action
   Trigger Hook : <e.g. On User Input of Field_X | On Validate | On Success>
   File Path    : scripts/<folder>/<filename>.deluge
   Fields Used  : [<Field_1>, <Field_2>, ...]
   Cross-Forms  : [<Related_Form_1>, ...]
   Purpose      : <Plain English summary of what this code executes>
   Optimization : <Notes on statement efficiency, batching, or query guards>
============================================================================== */
```

## 3. Deluge & Zoho One Optimization Guidelines

To guarantee high performance and avoid quota/statement bottlenecks:
1. **Never query inside loops**:
   - *Bad*: Querying related records for every row of a subform inside a `for each` loop.
   - *Good*: Collect IDs into a `List`, execute a single batch query `[ID in list_of_ids]`, store results in a `Map`, and retrieve in $O(1)$.
2. **Lean Field Footprint**:
   - Use Zoho Creator's native field formulas, default values, and lookup conditional filters where possible before falling back to Deluge script.
3. **Use Blueprints for Life Cycles**:
   - For multi-stage assets, orders, or transfers, use Zoho Creator Blueprints to define states, transitions, required transition fields, and validation rather than writing complex custom stage validation scripts.
4. **Stateless Forms for Complex Multi-Step Tasks**:
   - Use stateless forms for user-facing interactive actions (component swaps, delivery handovers, bulk month log generation). This keeps operational databases clean and avoids storing abandoned draft records.

## 4. User-to-Assistant Input Protocol

Whenever implementing or refining a module, the following details are coordinated:
1. **Form Link Name**: Exact internal API name of the form (e.g., `Lot_Master` vs `Lot_Masters`).
2. **Report Link Name**: Exact link name of the default report (e.g., `All_Lot_Masters`), used when querying records via Deluge.
3. **Field Link Names**: Exact API names of all fields referenced in workflows (e.g., `Lot_ID`, `Lot_Status`, `Manufacturing_Year`).
4. **Lookup Target Names**: Target form and displayed field names for relational fields.
